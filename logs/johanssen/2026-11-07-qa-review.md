# QA review workspace (T012-T014)

Asked Claude Code to build the QA tester role: a queue, a review page that compares the original and fixed code, test recording, approve or reject with feedback, and history. Before writing code, the agent read the spec, the existing `decide_fix` function, and teammates' code. It placed QA under `src/app/qa` and `src/lib/qa`, like Jordan's `developer` folders, so no teammate's files were edited, and it reused Joseph's `FixComparison` diff.

One design decision: QA rejection feedback must reach the Reporter (US3 scenario 2). The Reporter reads Joseph's `bug_feedback` table, and his migration says writers must take the author from the session. So `decide_fix` now writes the feedback there in the same transaction. Joseph's page shows it with no change to his code. Feedback is capped at 2000 characters to match his table, and longer text is refused rather than cut. I asked the agent to choose the queue order. It chose fixes awaiting QA first, oldest hand-off first, then everything else most recent first, and wrote tests for that rule.

Following the team workflow, the agent ran two independent read-only reviewers in parallel. The code reviewer found 1 medium issue and 2 low ones:
- the User Guide claimed History listed every version's tests when it only showed counts
- the decision confirmation message never appeared because the form unmounted
- SQL `btrim` stripped only spaces

The security reviewer checked forged revision IDs, grants, `search_path`, the `bug_feedback` insert and XSS against the local database, and found nothing exploitable. It flagged that `decide_fix` checked the stored `qa_id` but not the current role. All four were fixed: tests are now listed per version, a decision redirects to a banner that only shows when the status agrees, all whitespace is trimmed, and the current role is required. There are 3 new database tests.

Verified: 104 pgTAP tests, 34 vitest tests, lint, typecheck, production build. In a browser against the local stack I ran these paths:
- as QA:
  - an empty rejection is refused
  - a failing test is recorded
  - a rejection with feedback is saved
- as the Reporter: the feedback is visible
- as the Reporter: `/qa` is refused
- as QA, after re-seeding: a passing test is recorded
- as QA: an approval shows the banner and per-version history
